# Busker architecture

Busker is a Clojure HTTP server built on [libh2o] through the Java Foreign Function and Memory API.
This document describes its execution, response-storage and lifecycle contracts. The [ADRs](./adr/README.md) describe individual design decisions.

This document is for Busker contributors/maintainers as it only covers implementation details.
Familiarity with the [user-facing docs][docs] is a pre-req.

[libh2o]: https://github.com/h2o/h2o
[docs]: https://docs.outskirtslabs.com/ol.busker/next/

[!NOTE]
"Ring" (capitalized) refers to the Clojure HTTP convention, while "ring" refers to a ring buffer.

## Execution model

Each generation starts one native libh2o event loop which runs in one Clojure platform thread per worker.
The event-loop thread runs native polling, mailbox handling, response-ring draining, request registration, and resource retirement.
`ol.busker.worker-context` binds the current worker on that thread so response-head and fixed-final operations can reject calls from other threads without a dependency cycle.

App code / Ring request handlers code run on virtual threads.
It must not block in native calls.
Native callbacks copy or signal data, then dispatch application handling through the worker and callback-dispatch table.
No upcall lets a Throwable return to native code, since that ends the JVM. Each catches it and logs it under `:error`: the request callback answers 503; the body callback fails the request body, so the handler's next read throws an IOException and H2O answers 502 or resets the stream; the cleanup, proceed, stop and close callbacks log and return; and the TLS lookup fails the handshake. A failed accept gives back the connection slot, counts and socket it took and stops reading that listener until the next event-loop turn; a run of failed accepts lasts from the first failure to the next completed accept (an accept refused at the connection limit does not end it), and a worker whose run has lasted one second is failed.
Lifecycle work uses platform threads because it can wait for threads and native resources to finish.

When a worker finds no mailbox work and no new wake, it waits in three steps. If it has live requests and `:worker-hot-poll-micros` is positive (the default, 0, disables the poll), it first polls for up to that budget, spinning on its wake generation and mailbox count and running a zero-wait native turn every 5 microseconds so sockets keep being serviced. Work found by the poll is handled at once. When the budget runs out, when the poll is disabled, or when the worker has no live requests, it arms sleep and rechecks for work, then sleeps in `h2o_evloop_run` until a native wake or I/O ends the sleep, for at most 1 ms while request tasks are queued.

### Request dispatch

With `:request-threads :per-request`, the default, the request callback hands each request task to the generation's virtual-thread-per-task request executor, so every request runs on a new virtual thread. The worker record's `:request-dispatch` is nil in that mode, and the callback's only extra work is reading that field.

With `:request-threads :reuse-within-connection`, each worker has an `ol.busker.request-dispatch` state, and the callback passes the task with the request's connection id. Per worker, used only by the worker thread, there is an open-addressing table from connection id to drain state (`long[]` keys, 0 for a free slot, linear probing, deletion by backward shift, doubling at half load), a free list of drain states and a list of the states with queued tasks. A drain state holds a task queue, an active flag, the start time of its drainer's run, a move counter, a count of drainer threads running or starting on it, and a flag and link for a stack of states whose last drainer ended. The drain state itself is the Runnable the executor starts, and states come from the free list, so a request that arrives alone allocates nothing beyond the request task and thread of the default mode.

A request whose connection has no active drainer starts a virtual thread through the executor; that thread, the drainer, runs its request, then the requests of the same connection the worker queued meanwhile, one after another, and ends when the queue is empty. A drainer only ever polls the queue of the state it was started for, and a state serves one connection id at a time, so no thread runs requests of two connections. A request that arrives while its connection's drainer is active is queued, unless that drainer has run for longer than 100 microseconds; then the request goes to the executor directly. The drainer's run is timed from its first task, and the timer resets only when the drainer finds its queue empty and ends. Once per loop turn, and on each zero-wait turn of the hot poll while requests are queued, the worker starts a new thread for every queued request of a connection whose drainer has run that long, and while requests remain queued it waits at most 1 ms in `h2o_evloop_run`. Nothing wakes the worker when a drainer passes 100 microseconds, so a request waits in the queue for at most about 1 ms plus one loop turn, counted from when its drainer starts running. While the drainer waits for a carrier its run is not timed, so the requests queued behind it are not moved and run on it once it starts. The loop-turn pass visits only the states on the queued list and the states on the ended stack, not every connection.

The worker offers a task before it reads the drainer's active flag, and a drainer clears the flag before its last poll, so a queued task always has a drainer that polls after it was offered. A drainer that finds a task on that last poll but loses the flag to a newer drainer keeps running tasks of its connection, untimed, until the queue is empty. The worker counts each move as it starts and ends, and marks the start before it checks that a timed drainer still runs; a drainer whose last poll finds the queue empty while a move is under way waits for the move to end and polls again, so a task the move puts back always has a drainer to run it.

A drainer that brings its state's drainer count to 0 pushes the state on the ended stack with one compare-and-set. Once per loop turn the worker takes the whole stack and releases each state whose count is 0 and whose queue is empty: it leaves the table and goes to the free list. Only the worker queues tasks and starts drainers, so a released state holds no task and no thread uses it until the worker gives it to another connection. The count decides, not the active flag, because a drainer that lost the flag still polls its state's queue. A closed connection's state is released once its last drainer ends; its id is never used again. The table therefore holds at most one state per connection of that worker with a drainer running, starting or ended since the last turn. That includes closed connections whose handlers still run, which `:max-connections` no longer counts, so the bound is the worker's open connections plus its closed connections with running handlers, as the number of handler threads is in the default mode. The free list holds at most the table's largest size, and the table keeps that size.

When a stop begins, before it shuts the executor down, it marks each worker's dispatch as stopping, wakes the workers and waits up to 1 s in total for each worker's next sweep. That sweep starts a new thread for every queued request of every connection, whatever its drainer does, and from then on each new request goes to the executor directly, as in the default mode. Requests queued when the stop begins therefore run concurrently, not one after another on their drainer, provided each worker takes that turn: if a worker does not sweep within the second, or the stopping thread is interrupted, which ends every wait at once and keeps the interrupt set, the executor shuts down anyway and the queued requests of every worker that has not swept yet run one after another on their drainer. A request that arrives after the executor shuts down is not queued: the callback returns `CLJ_HANDLER_SHUTTING_DOWN` and the shim answers 503. Drainers are executor tasks, so stop waits for them, and a drainer runs every task still queued before shutdown. The loop-turn move does not move tasks while the executor is shut down; if the executor rejects a moved task, the task goes back in the queue and the move stops. Before `shutdownNow`, stop tells each worker's drainers to interrupt themselves before each remaining task, so those handlers see the interrupt as they would on separate threads. A handler that throws is reported through the thread's uncaught-exception handler and the drainer continues; the interrupt flag is cleared between tasks. If starting a drainer throws anything, the worker undoes the start, clears the active flag and treats the request as the default mode treats a failed start. If starting a drainer throws after an older drainer already took the request, the request runs there and the throwable is reported through the worker thread's uncaught-exception handler. Nothing bound to the thread is reset between tasks; for example `ThreadLocal` values, the thread's name, context class loader and uncaught-exception handler, its identity, held locks, and interrupts or unparks that application code sends after a request ended all reach the next task on that thread. Busker binds nothing to the thread per request.

### Accepting connections

Every worker reads a separate duplicate of each TCP or Unix socket listener, and the first worker to accept takes a connection. A generation counts the connections each of its workers holds, and a worker reads its listeners only while its count is not above the smallest count in the generation; the global `:max-connections` limit is checked first. An accept callback on a worker above the minimum stops reading without accepting, so the connection stays queued for a worker at the minimum. An accept that raises the minimum, which leaves the accepting worker at the minimum, wakes the other workers of its generation, so a sleeping worker that is now at the minimum starts reading again. A worker that stops for the global limit sets a generation flag; the next worker of that generation that finds the limit no longer reached clears the flag and wakes the others. A worker whose thread fails no longer counts toward the minimum. Connections never move between workers, so closes can leave the counts uneven until new connections arrive.

Each worker has a UDP socket for each HTTP/3 listener, all bound to the same address and port with `SO_REUSEPORT`, and the kernel picks the socket for a datagram by hashing its addresses. The shim counts the HTTP/3 connections of each worker per listener, separately from the TCP and Unix socket counts. A connection stops counting when quicly reports it closed, on entry to its closing or draining period, so connections that carry no more requests do not make a worker look loaded; one that ends without that report, after an idle or handshake timeout, stops counting when it is destroyed. A client that vanishes without closing still counts until the idle timeout. The connection keeps its connected socket and its slot in the global connection limit until it is destroyed. A worker that reads the first Initial of a new flow, in a datagram of at least 1200 bytes with connection IDs of the lengths quicly accepts, chooses among the accepting workers of the active generation the one with the fewest HTTP/3 connections and pending flows. It keeps the flow when it is at that minimum itself, counting the flows it kept in the same millisecond, since their accepts follow only after the whole receive batch; otherwise a cursor shared by the workers spreads ties, and the worker forwards the datagram to the chosen worker (see [HTTP/3 packet forwarding](#http3-packet-forwarding)). The forward adds a pending flow to the chosen worker before the write, and the chosen worker takes it back when it reads the datagram, whether or not it accepts a connection from it, so decisions made in between already see it. The deciding worker records each choice in a table of 64 entries and, for three seconds, sends the flow's later Initial and 0-RTT datagrams to the same worker. It overwrites only expired entries; while all are live, it keeps new flows and leaves them to the kernel's choice. If the first forward fails, because the chosen worker's channel is full or gone, the deciding worker accepts the flow and keeps its later datagrams; a later datagram that meets a full channel is dropped and sent again by the client, and one whose worker is gone stays with the deciding worker. Initial and 0-RTT datagrams that carry a connection ID issued by a worker of any generation on the listener go straight to that worker. A worker that stops accepting is not chosen, and a worker whose thread failed is not chosen again, even after a later activation.

Later packets of a moved connection still reach the first worker's socket, which forwards them by connection ID, until the connection's worker has a UDP socket for that connection alone (Linux only). When a worker processes forwarded datagrams of a connection whose TLS handshake is complete, it opens a socket bound with `SO_REUSEPORT` to the connection's local address and port and connected to the client's address, and reads it into the same QUIC context; the kernel then delivers that client's datagrams to the connected socket instead of the group. This applies to every connection whose datagrams arrive forwarded, also after a reload changed the group, and only after the handshake, so a client that has not received at its address never gets a socket. A listener has at most 64 such sockets over all workers and generations, because every datagram to the port that no connected socket takes is looked up past all of them. Sockets go to connections in the order their handshakes complete and stay with them until they close, so a connection that arrives when all are taken is forwarded for its whole life; therefore, while all 64 are in use, a worker keeps every new flow it reads, as the kernel placed it. Multicast, broadcast and IPv6 link-local addresses get no socket and stay forwarded. A failed system call stops new attempts on that worker for one second. The socket closes with its connection, or when its worker is disposed. When the client moves to another address or port, the worker replaces the socket with one connected to the new path, whether the new path's datagrams are forwarded to it or the kernel delivers them to its listener socket directly; while a worker has connected sockets it checks the path of each connection it reads on its listener socket, and a worker without any checks nothing. Datagrams already queued on the first worker's socket at the connect are still forwarded, so a few may arrive after later ones. Datagrams from other clients that reach the socket between its bind and its connect are handled as datagrams of the listener's socket.

### Native write completion

Workers submit responses on the event-loop thread, including between calls to `h2o_evloop_run`, while preserving one active native send per response. This requires completion delivery to record socket-interest reconciliation before the next poll. Otherwise an earlier update can retain write interest for an immediately completed write whose callback is then cleared.

The worker polls without waiting after a turn in which it handed output to H2O between event-loop runs, because H2O's poll wait does not account for completion callbacks already pending.

The pinned h2o-zig package builds H2O with the repair tracked in [H2O issue 3828](https://github.com/h2o/h2o/issues/3828): `run_socket` calls `link_to_statechanged(sock)` before `on_write_complete`. Recording the update before the callback permits rearm or close without accessing the socket afterwards. h2o-zig carries the repair as a patch file and applies it to every target; the native test `test_socket_write_completion.c` fails without it. The exact between-loop submission phase is not yet an upstream-confirmed API contract.

Normal shim builds run a Linux regression covering the stale-interest sequence, callback rearm, close and write errors. TCP/TLS stalled-reader tests check exact response bytes and backpressure. Cross-compilation does not establish kqueue runtime coverage; delayed zerocopy reclamation and asynchronous TLS paths require separate verification.

## Requests

The shim calls Clojure request callbacks with native request context data.
Busker copies request metadata into JVM memory before the native callback returns.
The handler thread decodes that copy when it reads the request, so decoding does not depend on the native request remaining valid.
Reading a key that the decoded Ring request never has, such as `:ol.busker/entrypoint` or a key added by middleware, does not decode it.
The entrypoint of a request is the entrypoint of the listener that accepted its connection. All listeners share one hostconf and one handler; each entrypoint has a small native record (`clj_entrypoint_hosts_t`) holding its index and a separate NULL-terminated hosts array that points at that hostconf. The accept contexts of the entrypoint's TCP and Unix socket listeners, and the accept context of each of its HTTP/3 worker contexts, use that array. H2O keeps the accept context's hosts pointer in every connection (HTTP/1, HTTP/2 over TLS, h2c prior knowledge and upgrade, HTTP/3) and only reads it to look up a host, so the request callback recovers the record from `req->conn->hosts` and copies the index into the request metadata. The request callback adds the matching entrypoint keyword to the lazy Ring request, so the dispatch pipeline reads it without decoding the request. A request whose connection has no known entrypoint is not dispatched: Busker logs it and the shim answers 500 (`CLJ_HANDLER_ERROR`); Debug builds of the shim assert instead.
The request metadata also carries H2O's connection id (`h2o_conn_t.id`), which H2O takes from one process-wide counter for HTTP/1, HTTP/2 and HTTP/3 connections and never reuses; a connection's address can be reused while Busker still runs a handler of the closed connection. Clojure reads the id from the native context as a primitive long, outside the request copy.
Streaming request bodies use a `java.nio.channels.ReadableByteChannel` and native proceed callbacks.
Callback-dispatch maps module and request sequence identifiers to live requests until cleanup.
Each request retains the generation configuration unchanged and references its worker. Streaming writers read the block pool and command services from that worker, passing the worker explicitly to each service.

## Responses

Internally there are two paths for responses to take: streaming responses or fixed-final.
A Ring response returned by a handler is sent down the fixed-final path when nothing has been written to its emitter, its status is 200 to 999 other than 204 and 304, and its body is a byte array or a string whose response charset is UTF-8, of at most `:output-buffer-size` and 32768 bytes.
This is a perf optimization so small requests can be sent in one clj->h2o operation.

Other supported bodies use the streaming path, which sends body data in chunks with backpressure to prevent the application from producing data faster than the client can read it. Every response head, including streaming and informational heads, must fit 64 header pairs and 16384 staging bytes. Excess headers cause an exception before acceptance; streaming does not increase header capacity.

### Fixed-final responses

The fixed-final path avoids the queue, writer, and chunk-handling overhead for small responses whose complete body is already available.
The term comes about from:

- fixed: the complete body and its byte length are known before sending
- final: It completes the response and no new body chunks will follow, that is, it is not an interim response such as `100 Continue`

The fixed-final path uses preallocated slots to reduce per-response allocation and pass complete responses from handler threads to the event-loop worker without waiting for native I/O.
The slots are `clj_response_slot_t` structs maintained in a ring-buffer in native memory.

When a Ring handler returns a response, Busker claims a slot, copies the headers and body into it.
It publishes the slot state, then its index in a capacity-sized ready bitmap, and requests a worker wake.
The worker detaches each bitmap word before processing its set bits, so publication during a drain remains discoverable without scanning every slot.
The slot keeps those bytes valid until native request cleanup, including after a final send returns. H2O reads the body directly from the slot; only headers are copied into its request pool. Cleanup detaches the slot reference and checks its claim token before making the slot reusable. Slots being filled survive concurrent disconnects until their producers return.

An `emit!` producer with `:end? true` on an emitter without earlier output also uses a slot, through a confined ByteBuffer view, when its capacity is at most 32768 bytes, the request method is not HEAD and the status is not 204, 205 or 304. Ring returns on this path use no streaming controller or receipt. Slot exhaustion parks a blocking caller or rejects a nonblocking operation; it does not select a second copying transport.

### Streaming responses

The streaming path handles incremental bodies, supported bodies beyond the fixed-body limits, responses that already sent informational headers, and Ring returns the fixed path does not take, such as nil bodies, 204 and 304 statuses, ByteBuffers and strings in other charsets. Those Ring returns create a streaming writer and an internal receipt. A platform thread allocates 256 native blocks per worker in a shared FFM arena. Each block has `:output-buffer-size` bytes (B). This reserves 8 MiB per worker at the default B=32768, separately from fixed slots. The worker sends descriptors for these blocks without copying their payloads. Blocking strings and ByteBuffers larger than B are encoded or copied straight into successive blocks; byte arrays are copied in B-sized pieces.

Each response admits one producer at a time. A bounded write reserves bytes, a block, a receipt and a mailbox permit before invoking application code. The callback runs synchronously on its calling virtual thread through a confined view of the shared block. Closing that view revokes application access before publication without freeing the backing storage. Neither close nor native cleanup waits for a callback to return while holding a lock.

Acceptance registers the output record and receipt atomically against closure. Reserved mailbox permits do not occupy FIFO positions: a slow private producer cannot prevent the worker from consuming published commands. Accepted records stay reachable until publication or explicit discard. The worker copies descriptors, not payload bytes, when combining native blocks into a send.

Three separate limits have separate release events. Pending byte credit is B per response and returns when records enter a native send. Each response has at most 64 unsettled receipts; receipt credit returns on settlement. Physical blocks remain checked out through native use. Each response has at most one native send, containing at most B bytes. Non-final proceed releases its blocks; final sends retain theirs until request cleanup. Native stop settles receipts but cannot release a still-live send.

One logical incremental write can publish a begin record, several data records and an EOF marker while retaining one receipt. Close captures only the accepted prefix, not future bytes or EOF from a blocked input source. A source that returns after close discards private bytes. Failure after begin acceptance terminates the response and returns the accepted receipt rather than reporting that no output was accepted.

Flush and end requests occupy coalesced per-response state, not mailbox entries. Each captures an accepted sequence prefix. The worker waits until that prefix has arrived before applying the control, so a control cannot overtake an accepted but unpublished head. Empty body writes are ordered local receipt markers, not empty intermediate native sends. Pressure flushes previously accepted output; global pool pressure tracks responses with unflushed blocks rather than scanning all requests.

Workers process bounded mailbox turns and one ready batch per selected response before polling native I/O. When H2O calls proceed during the send, so that the response is ready again at once, the worker sends up to 256 batches of that response in the same turn. Proceed can drain directly without another mailbox message, with reentrant callbacks handled by a trampoline. Unflushed output does not make the worker poll continuously. Close settles pending receipts immediately, independently of native storage release, and dispatches ordered callbacks on virtual threads.

The shim turns off H2O's `http1.req_io_timeout_while_generating` unless `:http1-req-io-timeout-while-generating?` is `true`, which the flat configuration passes through. With it off, the HTTP/1 request I/O timeout (`:http1-req-io-timeout`) covers receipt of the request and its body and each native send the client does not consume, but not the wait for the application's next output. A silent HTTP/1 stream stays open until the application writes or closes it, and Busker notices an idle client disconnect only at the next write. With it on, the timeout also runs while the response waits for the application, so H2O closes an HTTP/1 stream that stays silent longer than the timeout. HTTP/2 applies its idle timeout only to connections with no response waiting for the application; an HTTP/3 connection closes after the QUIC idle timeout without received packets.

If sending a returned Ring response throws while its emitter is open, Busker creates the streaming writer if necessary and requests an error-final send. The worker supplies a minimal status-200 head if no final head has started; this is a transport failure, not a successful empty response. Application failure checks admission and requests abort in one queue-lock transition. If `close!` or an accepted `:end? true` wins first, the accepted bytes and normal final send remain intact, including while awaiting mailbox consumption or native proceed. This also applies to incremental body-source failures. Publication, worker and native-send failures still discard pending output after admission closes: the transport can no longer deliver that prefix safely. A native stop notification records that transport has stopped and suppresses further sends. Failure and stop settle pending receipts without changing earlier results or releasing storage still in native use.

## Lifecycle

A generation is a running set of workers, listeners, and native resources.
During reload, Busker starts a new generation to accept new connections while the previous generation finishes work on its existing connections.
This lets configuration changes take effect without immediately interrupting active requests.

The previous generation stops accepting new connections but must still let its handlers send responses.
Busker keeps its response queues and native memory available until that work finishes or the shutdown timeout is reached.
Reaching the timeout does not make memory safe to free. Receiver admission closes first; previously entered producers and native requests retain their generation until publication, discard or cleanup. A producer that ignores interruption can delay release indefinitely. Failed retirement reports and retains the affected arenas and callback stubs instead of invalidating live addresses.

A worker fails when its event loop throws, or when a run of failed accepts lasts one second: `:on-native-failure!` stops the worker accepting, settles its live responses and ends its loop. When a generation stops after a worker failed and that worker's thread has ended, the stopping thread releases the worker's listener duplicates, stream pool, HTTP/3 worker contexts, receivers and context, the steps the worker's loop takes on a normal stop, and then releases the generation as usual, listener claims included. Each of these steps runs once, whether the worker took it before it failed or the stopping thread takes it. The failed worker's loop no longer runs, so nothing can close connections it still holds or settle blocks and responses still pending on it, and H2O does not allow a loop to be destroyed while timers of its connections are still set. When a failed worker left any of these, or its stream pool cannot retire, retirement still closes the generation's TCP and Unix socket listeners and releases their claims, so those ports refuse connections and can be bound again. It keeps the loops, contexts, receivers, HTTP/3 worker contexts and memory of the generation. It also keeps the HTTP/3 UDP sockets and their claims, because the kept HTTP/3 worker contexts still point at that transport. The UDP port therefore stays bound, and the kept sockets still receive a share of the datagrams sent to it. Retirement records the generation as kept before it releases the claims, and reports that worker threads ended with connections, responses or blocks nothing can finish. The kept connections also keep their slots in the process-wide connection limit. Every worker disposes its context once the connections it accepted have closed, so the other workers end even while a failed worker holds connections, and that report comes when they have ended, not at the timeout. Retirement reports a timeout only when a worker thread is still alive at the deadline.

Threads that publish a response or mailbox command call the native wake themselves, at most once per worker sleep. During context disposal, the event-loop worker directly retires its wake receiver: it quiesces the wake endpoint, waits for native wake calls in progress, closes the endpoint and unregisters the receiver before freeing it. A wake on a closed endpoint performs no native work.

If startup fails partway through, Busker attempts to stop the partial generation and rethrows the original startup error. Contexts without workers also have their wake and response receivers unregistered before context disposal. Cleanup cannot continue through dependent native resources when their safe release is uncertain. Such resources must remain allocated; an error or timeout is not evidence that native callers have finished.

### HTTP/3 packet forwarding

HTTP/3 contexts forward QUIC packets to the worker or generation selected by the connection ID, and the first datagrams of a new flow to the worker chosen for it.
Each worker reads forwarded packets from a socketpair, and the shim honours forwarding envelopes only on that socketpair, never on datagrams from the public UDP socket or from a connected socket.
The shim drops packets with a zero forwarding TTL and decrements TTL in each forwarded envelope.
This is an internal hop count, not the IP packet TTL; it prevents forwarding loops during routing and reloads.
On receipt, the shim caps TTL at the context's configured default and rejects envelopes without an IPv4 or IPv6 source address.
These checks are performed by Busker's callbacks, as required by the current libh2o callback contract.
Workers write to each other's socketpairs without taking a lock, and look workers up in a list of attached workers that is replaced, not changed. Each worker marks, in a counter only it writes, the stretch in which it uses that list and the workers it found in it; the flow table keeps a worker's ids, not a pointer to it. A register, unregister or activation replaces the list and then waits, holding the transport's mutex, until every worker that was in such a stretch has left it. Only then does it free the replaced list, and an unregister then also frees the departed worker's record and lets its write end close. If the shorter list cannot be allocated, the departed worker stays in the current list with its write end marked closed, so it is neither chosen nor written to, and its record is freed after the next list replaces that one. A listener therefore keeps one list and one record per attached worker, however many reloads it survives.
A datagram the shim sends to another worker stays in H2O's receive batch as a one-byte stub that fails to decode. When the callback drops a datagram instead, H2O processes the datagrams grouped before it in the batch with the dropped datagram's addresses.
H2O also forwards an Initial carrying another worker's connection ID only after trying to accept it, and the failed decryption overwrites the packet in place: its protected header bits and packet number, and the payload with the decryption output, so only the authentication tag is left as received. The shim therefore forwards those Initials itself, before H2O reads them, and its accept callback reports a failed decryption to H2O as no connection rather than as H2O's decryption-failed result, so H2O does not forward the overwritten bytes.
Native socketpair and loopback UDP regression tests cover these rules and the connected sockets, and run during normal shim builds.

### HTTP/3 key exchange

The HTTP/3 TLS context offers x25519, secp256r1 and secp384r1, in that order, the default of h2o's server. With the list picotls provides, secp256r1 alone, every client that sends no secp256r1 key share (curl and browsers send x25519 shares) would wait for a HelloRetryRequest, and picotls does not resume a session in a handshake that needed one. TCP listeners keep BoringSSL's default, which also offers X25519MLKEM768 first; h2o's server does not offer it over QUIC.

As in h2o's server, the HTTP/3 context resumes a session only with a new key exchange (psk_dhe_ke), so a ticket key that leaks later does not expose the data sent after the handshake of a resumed session (0-RTT data depends on the ticket alone in either mode); a client that lists psk_ke alone gets a full handshake.

### Early data

`:ol.busker/early-data?` is true when the TLS handshake of the request's connection had not finished when Busker handed the request to the handler. The shim reads it from h2o's `h2o_conn_is_early_data`, as h2o's proxy does for `Early-Data: 1`. Such a request arrived in 0-RTT data and may be a replay. A request sent in 0-RTT data reads false when the client's Finished reaches the server before the request is handed over, which is safe: a replayed first flight cannot finish the handshake. HTTP/3 listeners accept up to 8192 bytes of 0-RTT data, as h2o's server does.

TCP listeners accept no early data, since BoringSSL allows it only after `SSL_CTX_set_early_data_enabled`, which Busker does not call. `h2o_conn_is_early_data` reads only picotls state, which BoringSSL sockets lack, so on TCP it always returns false. Before TCP early data is turned on, the flag must therefore come from BoringSSL's `SSL_in_early_data` or `SSL_in_init`.

### QUIC address tokens

Address tokens are built as in h2o's server, from the session ticket keys. Each ticket key yields an AES-128-GCM token key: the SHA-256 digest of its cipher and HMAC keys, expanded with the HKDF label `address-token`. The first byte of the ticket key's name prefixes each token. Whenever the ticket key service loads, reseeds or rotates its key set, it drops the newer key of any two that share a first byte and creates a key if none is left active, and it gives every new key a first byte that no retained key uses. New tokens use the newest ticket key; a presented token is decrypted with the retained key its first byte names. Token keys therefore rotate, expire and survive reloads (or, with storage persistence, restarts) exactly as ticket keys do. Each HTTP/3 worker keeps a separate set of cipher contexts for every ticket key, used only on its loop, and rebuilds them when the ticket manager's key generation changes.

Busker sends NEW_TOKEN frames when quicly and libh2o ask for them. On accept, a resumption token from the same IP address and at most ten minutes old validates the client's address; an older token, or one from another address, leaves the address unvalidated, and a token that no retained key decrypts is ignored. A Retry-type token whose first byte names a retained key but that does not decrypt is answered with INVALID_TOKEN; with any other first byte, or on a worker without token keys, it is ignored. Busker never sends Retry, as h2o does not by default. When session tickets are disabled, workers have no token keys: presented tokens are ignored and NEW_TOKEN frames carry random bytes of a real token's length, which no server accepts, because quicly offers no way to skip a requested token.
